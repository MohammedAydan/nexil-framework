# Nexil v1.1.0: محرك منع التكرار وتحسين تجربة المطور

يوسّع Nexil v1.1.0 سطح الإنتاج في v1.0.0 بإضافة الاستدلال التلقائي لحدود الاستئناف، وإزالة تكرار ScopeRef هرميًا، والتخطيطات المتداخلة، وتوارث بيانات metadata، وبث Suspense خارج ترتيب المصدر، والنماذج التدريجية، وTyped Loaders، وسير عمل CLI أكثر اكتمالًا، وتشغيل إنتاجي دون تهيئة إلزامية، وأدوات أولية للجلسات والتفويض.

> يصف هذا الدليل السلوك الموجود في الفرع `main`. تحقّق دائمًا من ملفات `.d.ts` و`nexil-manifest.json` والمخرجات الفعلية للإصدار الذي ستنشره.

## أهم التغييرات

يستدل المترجم الآن على حدود الاستئناف الآمنة من JSX وTSX العاديين. فالقراءات المباشرة مثل `{count()}` تتحول إلى ربط نصي دقيق عندما يكون المصدر Signal قابلًا للاستئناف، كما تُحوّل خصائص `value` و`checked` و`disabled` و`hidden` و`className` و`href` و`src` التفاعلية إلى أهداف DOM المقابلة. تبقى التوجيهات الصريحة مفيدة عندما يلزم توضيح النية:

```tsx
import { state } from '@nexil/core'

const name = state('Ada')
const busy = state(false)

export default function Profile() {
  return (
    <form>
      <input bindValue$={name} aria-label="Name" />
      <button bindDisabled$={busy} type="submit">
        Save {name()}
      </button>
    </form>
  )
}
```

يستخدم المترجم تحليل AST لتقييم القيم الابتدائية الحرفية، ويصدر تشخيصات للالتقاطات غير الآمنة، ويستخدم تجزئة معيارية للتعبيرات المتساوية كي تشترك في chunk كسول واحد. يُصدر البناء runtime المناسب فقط: `nexil-bootstrap.js` للأحداث، و`nexil-bindings.js` للربط، و`nexil-forms.js` فقط للمسارات التي تحتوي `Form` تدريجيًا.

## إزالة تكرار ScopeRef

ترفع عملية البناء حمولات `data-nx-scope` المتطابقة إلى أقرب سلف مشترك لها في HTML المُولّد، وتزيل النسخ المتكررة من الأبناء. لا تغيّر هذه العملية ABI الخاص بالربط. لذلك يُفضّل استخدام Signals وstores العادية بدل استدعاء التسلسل يدويًا في صفحات التطبيق.

> لا تستدعِ `serializeScopeRefs()` داخل مكونات المسارات العادية. تبقى هذه الدالة مناسبة لاختبارات runtime وadapter منخفضة المستوى، وليست واجهة التأليف المعتادة.

## التخطيطات المتداخلة وتوارث metadata

الملفات المسماة `_layout.tsx` هي وحدات تركيب وليست مسارات مستقلة. يدعم اكتشاف التخطيطات التداخل والـ route groups؛ تستقبل التخطيطات `children`، ويمكنها تصدير `seo` يرثه الأبناء.

```tsx
// src/routes/_layout.tsx
export const seo = {
  title: 'Nexil App',
  titleTemplate: '%s · Nexil App',
  openGraph: { siteName: 'Nexil App' },
}

export default function RootLayout({ children }) {
  return (
    <>
      <header>
        <a href="/">Nexil App</a>
      </header>
      <main>{children}</main>
    </>
  )
}
```

يمكن للمسار الابن تجاوز أي قيمة مع الاحتفاظ بقالب العنوان وإعدادات الموقع الموروثة. لا تصبح أسماء route groups أجزاء من URL العام، لكنها تبقى متاحة لتركيب التخطيطات.

## بث Suspense خارج ترتيب المصدر

أصبحت `Suspense` عقدة render مستقلة. يرسل stream الغلاف وfallback فورًا، ثم يرسل قوالب الحدود التي اكتملت دون انتظار الحدود السابقة في ترتيب الملف.

```tsx
import { Suspense } from '@nexil/core'

export default function Dashboard() {
  return (
    <main>
      <h1>Dashboard</h1>
      <Suspense id="activity" fallback={<p>Loading activity…</p>}>
        {loadActivity().then((items) => (
          <Activity items={items} />
        ))}
      </Suspense>
    </main>
  )
}
```

يجب أن يكون لكل boundary معرف فريد، وأن يتكوّن من أحرف وأرقام و`_` أو `-` فقط.

## النماذج التدريجية والأفعال المعيّنة

تحافظ `Form` على مسار الإرسال الأصلي للمتصفح عند غياب JavaScript، وتضيف metadata للتحسين التدريجي. وتتيح `SubmitButton` نصًا لحالة التحميل. يقوم runtime المُولّد بالحفاظ على الحقول المتكررة، وإنشاء idempotency key، وإرسال CSRF اختياري، وتعطيل زر الإرسال مؤقتًا، وإطلاق حدثي `nexil:form-success` و`nexil:form-error`.

```tsx
import { Form, SubmitButton } from '@nexil/core'
import { action } from '@nexil/actions'

const saveProfile = action({
  endpoint: '/__nexil/actions/profile/save',
  validate: (input) => input,
  handle: async (_context, input) => ({ saved: input }),
})

export default function ProfileForm() {
  return (
    <Form action={saveProfile} csrfToken={csrfToken}>
      <input name="displayName" required />
      <SubmitButton loadingText="Saving…">Save</SubmitButton>
    </Form>
  )
}
```

يجب أن يفرض endpoint التحقق والتفويض وOrigin الموثوق وتخزين idempotency محدودًا وحدود حجم الطلب. تحسين المتصفح ليس حدًا أمنيًا.

## Typed Loaders وcookies و404

يوفر package الخادم `defineLoader` و`parseCookies` و`getCookie` و`notFound()` للاستعمال مع request-scoped data:

```ts
import { defineLoader, getCookie, notFound } from '@nexil/server'

export const loadAccount = defineLoader(async ({ request, params }) => {
  const session = getCookie(request, 'session')
  if (!session) throw notFound()
  return getAccount(params.id, session)
})
```

يبقى فك cookie غير صالح دون خسارة للقيمة الأصلية، ولا تعتمد loaders على singleton قابل للتعديل.

## مسار الإنتاج دون تهيئة إلزامية

تتبع المشاريع الجديدة مسارًا واحدًا:

```bash
pnpm dev
pnpm build
pnpm start
```

ينسخ `nexil build` أصول التطبيق الآمنة من `public/` إلى `dist/client`. يتطلب `nexil start` مخرجات البناء ثم يقدمها بخادم Nexil الإنتاجي، محافظًا على دلالات المسارات وActions وسياسة cache وسلوك 404/405/HEAD. يبقى `nexil preview` و`nexil serve` متاحين للتوافق.

استخدم `defineConfig` من `@nexil/serve` فقط عندما تحتاج إلى تغيير الأصل العام أو host أو port أو أصول Actions أو redirects أو feeds أو سياسة cache.

## واجهات الخادم وMiddleware الواضحة

استخدم `createServer` و`createMiddleware` و`composeMiddleware` من `@nexil/serve` في المشاريع الجديدة. تبقى `createProductionServer` و`createProductionMiddleware` أسماء متوافقة. تعمل Middleware التطبيق قبل معالجة المسار وAction، ويجب أن تستدعي `next()` مرة واحدة على الأكثر.

واجهة Middleware هذه تعتمد على `IncomingMessage` و`ServerResponse` في Node. في بيئات Edge وDeno استخدم تكوينًا مكافئًا لمعالجات Fetch بدل استيراد طبقة Node.

## أدوات الجلسات والتفويض

توفر `@nexil/security` دالة `createSession` المستقلة عن التخزين، وفحوص الدور والصلاحية، و`requireAccess` لسياسات المورد أو المستأجر التي يملكها التطبيق. تتلقى الحزمة `SessionStore` من التطبيق، ولا تنفذ مزود OAuth/OIDC أو قاعدة مستخدمين أو مسار بيانات اعتماد أو واجهة تسجيل دخول مستضافة.

أبقِ التفويض داخل Action أو حد الخادم الذي يملك المورد حتى عندما تقرأ Middleware الجلسة؛ فالـ cookie وحده لا يثبت الملكية أو الصلاحية.

## قائمة الترقية

1. أعد تسمية ملفات التركيب من `layout.*` إلى `_layout.*` عند اعتماد convention التخطيطات الجديد؛ ما زالت الملفات القديمة مدعومة للتوافق.
2. أزل الاستدعاءات اليدوية لـ`serializeScopeRefs()` من مكونات المسارات.
3. استخرج الغلاف المتكرر إلى تخطيط root وتخطيطات متداخلة.
4. استخدم `Form` و`SubmitButton` بدل fetch اليدوي للنماذج، واحتفظ بـ`onSubmit$` فقط عند الحاجة إلى عرض نتيجة مخصص.
5. حدّث افتراضات المخرجات لتشمل `nexil-forms.js` و`nexil-chunks/`.
6. احذف سكربتات المشروع التي تنسخ `public/` يدويًا إلى `dist/client` بعد الترقية إلى v1.1.0.
7. استخدم `createServer` و`createMiddleware` و`composeMiddleware` في الكود الجديد؛ تبقى الأسماء الإنتاجية القديمة صالحة.
8. شغّل build وtypecheck وlint وformat والاختبارات وparity والميزانية وsecurity وE2E قبل النشر.

## التوافق والتحقق

تحافظ v1.1.0 على عقود render وadapters في v1.0.0. التغيير الأساسي هو أن أنماط تأليف أكثر تُحوّل تلقائيًا؛ أما التعبيرات الديناميكية غير القابلة للإثبات فتبقى SSR عاديًا وتنتج تشخيصًا يقترح directive صريحًا. تواصل المسارات الثابتة إرسال صفر JavaScript خاص بالمسار.

تغطي بوابة الإصدار build وtypecheck وlint وformat والاختبارات وruntime parity والميزانية والتدقيق الأمني وتقييم showcase واختبارات المتصفح. راجع [الفهرس العربي](../ar/README.md) و[الفهرس الإنجليزي](../en/README.md) و[ملاحظات v1.1.0 الإنجليزية](./v1.1.0.md) قبل النشر.
