# Nexis v1.1.0: Zero-Duplication Engine and Developer Experience

Nexis v1.1.0 extends the v1.0.0 production surface with compiler-inferred resumability, hierarchical scope deduplication, nested layouts, metadata inheritance, out-of-order Suspense streaming, progressive forms, typed loaders, and a more complete CLI workflow.

> The examples in this guide describe the implementation on the `main` branch. Always validate the generated manifest and output directory for the exact package version being deployed.

## What changed

The compiler now infers safe resumable boundaries from ordinary JSX and TSX authoring. Direct reads such as `{count()}` are lowered to fine-grained text bindings when the dependency is a statically resumable Signal. Direct reactive DOM properties such as `value`, `checked`, `disabled`, `hidden`, `className`, `href`, and `src` are lowered to their corresponding DOM targets. Explicit directives remain available when intent must be unambiguous:

```tsx
import { state } from '@mohammedaydan/core'

const name = state('Ada')
const busy = state(false)

export default function Profile() {
  return (
    <form>
      <input bindValue$={name} aria-label="Name" />
      <button bindDisabled$={busy} type="submit">
        Save {name()}
      </button>
    </form>
  )
}
```

The compiler uses AST-based literal evaluation for initial values, emits diagnostics for unsafe captures, and hashes equivalent handler expressions to one lazy chunk. A generated route receives only the runtimes it needs. `nexis-bootstrap.js` serves event resumability, `nexis-bindings.js` serves Signal-to-DOM bindings, and `nexis-forms.js` is emitted only when a route contains a progressive `Form`.

## Scope payload deduplication

Scope payloads are now lifted hierarchically in generated HTML. When identical `data-nx-scope` envelopes occur in sibling subtrees, the build places one envelope at their nearest shared ancestor and removes the redundant child copies. This reduces repeated serialized state without changing the DOM binding ABI. Applications should therefore prefer compiler-inferred bindings over manual serialization.

```tsx
import { state } from '@mohammedaydan/core'

const count = state(0)

export default function Counter() {
  return <button onClick$={({ element }) => count.set(count() + 1)}>{count()}</button>
}
```

Do not call `serializeScopeRefs()` in ordinary route components. That low-level helper remains useful for runtime and adapter tests, but application code should expose supported values through normal Signals, stores, and action references.

## Nested layouts and metadata inheritance

Files named `_layout.tsx` are composition modules rather than standalone routes. Layout discovery is recursive and supports route groups. A layout receives the rendered child content through `children` and may export `seo` metadata that is inherited by descendants.

```tsx
// src/routes/_layout.tsx
export const seo = {
  title: 'Nexis App',
  titleTemplate: '%s · Nexis App',
  openGraph: { siteName: 'Nexis App' },
}

export default function RootLayout({ children }) {
  return (
    <>
      <header>
        <a href="/">Nexis App</a>
      </header>
      <main>{children}</main>
      <footer>Built with Nexis</footer>
    </>
  )
}
```

A child route may override any inherited field while retaining the parent template and site settings:

```tsx
export const seo = {
  title: 'Architecture',
  description: 'How the Nexis runtime is organized.',
}
```

The generated head contains one structural charset and viewport declaration, one canonical, and one effective value for each inherited metadata key. Route groups retain their directory names for layout composition but do not become public URL segments.

## Out-of-order Suspense streaming

`Suspense` is a first-class render node. The stream flushes the shell and fallback immediately, then sends resolved boundary templates as each asynchronous child completes rather than waiting for boundaries in source order.

```tsx
import { Suspense } from '@mohammedaydan/core'

export default function Dashboard() {
  return (
    <main>
      <h1>Dashboard</h1>
      <Suspense id="activity" fallback={<p>Loading activity…</p>}>
        {loadActivity().then((items) => (
          <Activity items={items} />
        ))}
      </Suspense>
    </main>
  )
}
```

Boundary identifiers must be unique within a document and must contain only letters, numbers, underscores, or hyphens. The stream renderer uses inert template payloads and replacement scripts so the initial shell remains valid HTML and does not require whole-page hydration.

## Progressive forms and typed actions

`Form` keeps the native browser submission path while adding opt-in enhancement metadata. `SubmitButton` exposes a loading label. The generated forms runtime serializes repeated fields losslessly, adds an idempotency key, includes an optional CSRF header, disables the submit control during the request, and emits `nexis:form-success` or `nexis:form-error` events.

```tsx
import { Form, SubmitButton } from '@mohammedaydan/core'
import { action } from '@mohammedaydan/actions'

const saveProfile = action({
  endpoint: '/__nexis/actions/profile/save',
  validate: (input) => input,
  handle: async (_context, input) => ({ saved: input }),
})

export default function ProfileForm() {
  return (
    <Form action={saveProfile} csrfToken={csrfToken}>
      <input name="displayName" required />
      <SubmitButton loadingText="Saving…">Save</SubmitButton>
    </Form>
  )
}
```

The server action endpoint must still enforce validation, authorization, trusted-origin checks, bounded idempotency storage, and request-size limits. Client enhancement is not a security boundary.

## Typed loaders, cookies, and 404 responses

The server package provides reusable request-scoped loaders, safe cookie parsing, and a standards-compatible `notFound()` response:

```ts
import { defineLoader, getCookie, notFound } from '@mohammedaydan/server'

export const loadAccount = defineLoader(async ({ request, params }) => {
  const session = getCookie(request, 'session')
  if (!session) throw notFound()
  return getAccount(params.id, session)
})
```

Cookie decoding is lossless when a value is malformed, and loaders receive the request, route parameters, and request-scoped data context without relying on mutable module state.

## CLI additions

The CLI now documents and supports the following workflow:

| Command                           | Purpose                                                                                                        |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `nexis dev`                       | Run the Vite development server with SSR middleware.                                                           |
| `nexis build`                     | Build route HTML, server modules, assets, lazy chunks, runtimes, feeds, redirects, OG cards, and the manifest. |
| `nexis preview`                   | Preview the production output locally.                                                                         |
| `nexis start` / `nexis serve`     | Start the production server or static route server.                                                            |
| `nexis generate route <path>`     | Create a route module safely below `src/routes`.                                                               |
| `nexis generate component <name>` | Create a component below `src/components`.                                                                     |
| `nexis add action <name>`         | Create a server action scaffold below `src/actions`.                                                           |
| `nexis routes`                    | List discovered routes and layout boundaries.                                                                  |
| `nexis analyze`                   | Report route bytes, interactivity, bindings, and generated chunks.                                             |
| `nexis doctor`                    | Check package metadata, shell markers, and route structure.                                                    |
| `nexis check --budget`            | Run build and output-budget checks.                                                                            |
| `nexis test`                      | Run the repository-integrated test workflow.                                                                   |
| `nexis upgrade`                   | Scan dependencies and source conventions for migration work.                                                   |

## Migration checklist

1. Rename application composition files from `layout.*` to `_layout.*` where the new recursive layout convention is desired. Legacy `layout.*` files remain recognized for compatibility.
2. Remove manual `serializeScopeRefs()` calls from route components and replace them with ordinary Signal, store, or action references.
3. Replace repeated page shells with root and nested layouts.
4. Replace hand-written progressive form fetch code with `Form` and `SubmitButton`; retain a declarative `onSubmit$` boundary only when the page needs custom result rendering.
5. Update documentation and generated output assumptions to include `nexis-forms.js` and nested `nexis-chunks/` assets.
6. Run `pnpm build`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check`, `pnpm test`, `pnpm test:parity`, `pnpm check:budget`, `pnpm security`, and `pnpm test:e2e` before deployment.

## Compatibility notes

The v1.1.0 APIs preserve the v1.0.0 rendering and adapter contracts. The principal behavior change is that more authoring patterns are lowered automatically. Dynamic expressions that cannot be proven safe remain ordinary SSR output and produce a diagnostic recommending an explicit binding directive. Static routes continue to ship zero route-specific JavaScript, and interactive output remains governed by the configured byte budgets.
