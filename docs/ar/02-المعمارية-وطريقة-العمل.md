# 02 — المعمارية وطريقة عمل الفريمورك

## الصورة الكاملة

يتكون Nexil من حزم صغيرة، لكل حزمة مسؤولية محددة. هذا يسمح باستخدام أجزاء من الفريمورك مستقلًا، ويساعد على اختبار كل طبقة دون تشغيل تطبيق كامل.

| الطبقة      | الحزمة               | المسؤولية                                        |
| ----------- | -------------------- | ------------------------------------------------ |
| النواة      | `@nexil/core`        | أنواع RenderNode وChild وElement                 |
| التوجيه     | `@nexil/router`      | تحويل أسماء الملفات إلى RouteRecord ومطابقة URL  |
| الرندر      | `@nexil/renderer`    | تحويل شجرة JSX/RenderNode إلى HTML أو Stream     |
| التفاعل     | `@nexil/reactivity`  | Signal وComputed وEffect وBatch وCleanup         |
| الحالة      | `@nexil/state`       | Store وSelectors وStateRegistry                  |
| العميل      | `@nexil/client`      | ScopeRef registry واستعادة المراجع               |
| Compiler    | `@nexil/compiler`    | ميزانيات JavaScript وتحليل الحدود                |
| Vite plugin | `@nexil/vite-plugin` | تحليل المصدر وإنتاج Bootstrap وchunks            |
| CLI         | `@nexil/cli`         | اكتشاف routes وبناء HTML والأصول                 |
| Server      | `@nexil/serve`       | خدمة dist رسميًا في الإنتاج                      |
| Actions     | `@nexil/actions`     | التحقق والتنفيذ والتكرار والأصل                  |
| SEO         | `@nexil/seo`         | Head وSitemap وFeeds وJSON-LD                    |
| Media       | `@nexil/media`       | Variants وPicture markup والتخزين المؤقت         |
| Telemetry   | `@nexil/telemetry`   | أحداث منخفضة الكاردينالية وWeb Vitals الاختيارية |

## مرحلة التطوير

أثناء التطوير يشغل Vite dev server. يكتشف Vite plugin ملفات routes، يحلل handlers التي تنتهي بـ `$`، ويولد chunks مؤقتة. عند طلب الصفحة، يعيد Dev server بناء Request Web ويرسلها إلى render pipeline. في وضع Proxy الموثوق، يمكن تفعيل `NEXIS_TRUST_PROXY=1` فقط خلف Proxy ينظف `x-forwarded-*`.

## مرحلة البناء

أمر `nexis build` يمر بالمراحل التالية:

1. يقرأ `nexis.config.json` أو `nexis.config.js` أو `nexis.config.mjs` أو `nexis.config.ts`.
2. يكتشف ملفات routes ويحولها إلى RouteRecord.
3. يبني route template وHead العام.
4. يرندر كل route في وضعه المحدد.
5. يوسع `getStaticPaths` للمسارات الديناميكية.
6. يجمع CSS ويكتب ملفات HTML.
7. يولد Bootstrap وchunks فقط للمسارات التفاعلية.
8. يخرج Sitemap وRobots وRSS وAtom وRedirect manifest.
9. يولد OG cards وMedia variants عند تفعيلها.
10. يكتب `nexis-manifest.json` ومؤشرات الأصول.

## دورة طلب الصفحة

في الإنتاج، يستقبل `@nexil/serve` طلبًا. يطابق المسار مع ملفات `dist/client`، ثم:

- يخدم `index.html` للمسار `/` أو للمسارات المتداخلة.
- يخدم الملفات الثابتة مع MIME مناسب وCache immutable للأصول fingerprinted.
- يقبل `GET` و`HEAD`.
- يرد بـ `405` للطرق غير المسموح بها على الملفات الثابتة.
- يرفض مرشحات Path traversal.
- يخدم 404 مخصصًا أو 404 افتراضيًا.
- يمرر Action routes إلى transport الخاص بها.
- يمرر Telemetry receiver الاختياري إلى callback التطبيق.

## RenderNode

الـ Renderer لا يفترض DOM. هو يعمل على أنواع مجردة مثل النص، العناصر، Arrays، وPromises. لذلك يمكن تشغيله في Node أو Deno أو Edge دون الاعتماد على browser globals.

```ts
import { renderToStringAsync } from '@nexil/renderer'

const html = await renderToStringAsync({
  type: 'main',
  props: { class: 'page' },
  children: ['Hello from Nexil'],
})
```

يتم Escape للنصوص والخصائص بحسب نوعها. لا تضع HTML خامًا من مستخدم داخل `dangerously` أو أي مسار غير موثوق؛ يجب تحويل البيانات إلى نص آمن أو تنظيفها بسياسة واضحة.

## Compiler وBootstrap

يفحص Vite plugin دوال التفاعل lazy ويكتب لكل واحدة chunk. Bootstrap واحد صغير يلتقط الأحداث delegated، يقرأ `data-nx-scope` و`data-nx-on-*`، ثم يستورد chunk الخاص بالعنصر. إذا كانت الصفحة غير تفاعلية فلا يجب أن تشحن JavaScript خاصًا بها.

القاعدة التصميمية هي أن Bootstrap ليس مكان منطق التطبيق. يجب أن يبقى عامًا وصغيرًا، بينما يبقى منطق الصفحة داخل lazy chunk.

## ScopeRef Registry

`ScopeRef` هو عقد ABI بين الخادم والعميل. بدل تمرير Closure أو object عشوائي، يسجل الفريمورك نوع المرجع ومعرفه:

```ts
type ScopeRef =
  | { kind: 'value'; id: string; value: unknown }
  | { kind: 'signal'; id: string }
  | { kind: 'store'; id: string }
  | { kind: 'action'; id: string }
  | { kind: 'unsupported'; id: string; reason: string }
```

المراجع غير المدعومة لا تُسلسل بصمت. تظهر كتحذير أو تصنيف `unsupported` حتى لا يتصرف التطبيق بطريقة مختلفة في الإنتاج.

## لماذا الفصل بين الحزم مهم؟

الفصل يمنع أن تعتمد SEO على DOM، أو أن يعتمد Renderer على Node، أو أن يستدعي Client قاعدة بيانات. هذه الحدود تجعل الاختبارات أصغر وتسمح بتشغيل Handler واحد خلف Node أو Deno أو Cloudflare.
