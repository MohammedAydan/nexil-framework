# 13 — الاختبار والأداء

## طبقات الاختبار

لا يكفي اختبار component واحد. بنية Nexis تحتاج ثلاث طبقات:

| الطبقة         | ماذا تختبر                                                   |
| -------------- | ------------------------------------------------------------ |
| Unit           | Signal وSEO وRouter وAction وMedia وRenderer                 |
| Integration    | build وCLI وScopeRef وserver routes                          |
| E2E            | browser، chunks، native forms، routes، layouts، 404، console |
| Runtime parity | Node وDeno وCloudflare وFetch contracts                      |
| Benchmark      | bytes، latency، SEO، feed، media، redirects                  |

## أوامر التحقق

```bash
pnpm build
pnpm typecheck
pnpm test
pnpm test:parity
pnpm check:budget
pnpm test:node-runtime
pnpm test:edge
pnpm test:e2e
pnpm lint
pnpm format:check
pnpm audit --audit-level=high
pnpm test:deno:e2e  # يحتاج executable Deno فعليًا
git diff --check
```

الأمر `test:deno:e2e` يحتاج executable `deno` فعليًا. لا تستبدل نجاح Node strip-types بادعاء أن Deno اشتغل.

## اختبارات Resumability

في E2E راقب:

- عدم وجود application handler أثناء initial paint.
- عدم وجود JavaScript في static route.
- تحميل bootstrap عند الحاجة.
- تحميل chunk المناسب عند النقرة.
- تحميل `nexis-bindings.js` للـ bindings فقط و`nexis-forms.js` للنماذج فقط.
- عدم تكرار handler chunks أو `data-nx-scope` envelopes المتطابقة.
- تركيب `_layout.*` مرة واحدة مع metadata موروثة دون duplicate head tags.
- تغير النص أو state دون navigation كامل.
- نظافة console.

## ميزانية العميل

الـ compiler يطبق حدودًا مثل Bootstrap أقل من 2048 bytes raw، وقيود chunks وgzip. لا ترفع الحد لمجرد تمرير build؛ وثّق سبب الزيادة وقِس أثرها.

```text
Route static     → 0 route-specific JS
Route interactive → bootstrap + smallest lazy chunk
```

## جرد الأصول الثابتة

بعد `nexis build` شغّل `nexis analyze` لمراجعة أصول التسليم الناتجة بجانب ميزانيات JavaScript الخاصة بالـRoutes. يعرض الأمر عدد الملفات غير HTML، وإجمالي حجمها، وحجم الصور، وأكبر خمسة أصول. الصورة التي تبلغ 256 KiB أو أكثر تحصل على تنبيه وقت البناء. التنبيه لا يوقف الـbuild عمدًا لأن الحد الصحيح يتغير بحسب نوع المحتوى ومسار المستخدم ودور الصورة في LCP.

```text
Static asset delivery
18 files  612.4 KiB total  430.1 KiB images
Largest assets:
  /hero.png  420.0 KiB  image  warning: consider AVIF/WebP variants, `sizes`, and lazy loading when below the fold
```

فضّل AVIF/WebP مستجيبة مع fallback مناسب، وأبعاد أصلية، و` sizes` صحيح. اجعل صورة LCP المرئية فقط ذات أولوية عالية، واستخدم lazy loading عادة للصور أسفل الجزء المرئي. افحص الـRoute المنشور في متصفح ومع CDN حقيقيين قبل تحويل التنبيه إلى سياسة تمنع الإصدار.

## مقارنة Astro

`bench:compare` يقارن route equivalent، لا كل chunks الموقع مجتمعة. يجب أن تكون baseline عادلة: نفس HTML التقريبي، نفس interaction، ونفس asset. احفظ files المقاسة داخل artifact حتى يمكن مراجعة الرقم.

## Lighthouse

`bench:lighthouse` يشغل audits mobile على routes السبعة ويطبق gates للـ SEO والأداء والوصولية. هذه lab scores تتأثر بنسخة Chromium وCPU والتخزين المؤقت.

لا تستخدم score محليًا كبديل عن Real User Monitoring. افصل بين:

- Lab: Lighthouse.
- Field: telemetry وCore Web Vitals من مستخدمين حقيقيين.
- Server: latency وerror rate وcache hit.

## قياس server

Benchmark production يقيس عددًا من الطلبات المتتابعة على localhost. هذه الأرقام لا تشمل TLS أو CDN أو DNS أو cold start أو شبكة المستخدم. استخدم median وp95 عند توفر عدد كافٍ من العينات، ولا تستنتج traffic أو rankings.

## اختبارات النماذج التدريجية

اختبر native submission عند تعطيل JavaScript، ثم enhanced submission عند تفعيله. تحقق من الحقول المتكررة، وIdempotency-Key، وCSRF header، وحالة تحميل الزر، وأحداث النجاح والفشل.

## اختبارات stream

اختبر parity بين buffered وstreamed HTML، وfallback الخاص بـSuspense، ووصول boundaries المكتملة خارج ترتيب المصدر، وchunk bounds، وbackpressure، وabort، وcancellation hook، وقرار إغلاق stream عند انقطاع العميل.

## اختبارات SEO

اجمع كل published routes، وتحقق من title وdescription وcanonical وOG وTwitter وJSON-LD وdangerous URLs وbroken links وduplicate signatures وsitemap وrobots وfeed.

## اختبارات الأمان

اختبر input malformed، Origin، duplicate idempotency، request size، path traversal، method rejection، cookies، headers، وJSON-LD escaping. لا تعتبر `pnpm audit` بديلًا عن مراجعة threat model.

## التعامل مع flaky tests

لا تعيد الاختبار حتى ينجح وتخفي المشكلة. سجّل البيئة والـ port والـ process state. أوقف dev servers القديمة، أصلح workspace links، وامسح artifacts المؤقتة قبل إعادة التجربة.

## تقرير الأداء

يجب أن يذكر التقرير:

- commit وNode وpnpm وbrowser versions.
- routes التي قيسَت.
- raw/gzip bytes.
- local أو remote nature للقياس.
- thresholds والنتيجة.
- القيود وما لا يمكن استنتاجه.

## مختبر Workbench

ابدأ بـ`pnpm --filter @mohammedaydan/example-nexis-workbench verify`. ثم أضف browser assertions لـHTML الأولي وanchors بلا JavaScript وLink history/bypasses وأول تفاعل filter و404 وnative support-form submission. افصل هذه assertions عن اختبارات authentication أو database خاصة بمزود خارجي، وسجّل البيئة إلى جانب قياسات الأداء.
