# 07 — الحالة والتفاعلية

## طبقات الحالة

اختر أصغر مستوى يناسب الحالة:

| المستوى | مثال                        | مكانها                  |
| ------- | --------------------------- | ----------------------- |
| محلية   | فتح/إغلاق قائمة             | داخل المكون             |
| مشتركة  | سلة المستخدم في عدة مكونات  | Store مشترك             |
| Route   | نتيجة بحث route             | طبقة route أو loader    |
| Layout  | تفضيل اللغة في مجموعة صفحات | Store مملوك للـ layout  |
| عالمية  | إعدادات التطبيق العامة      | StateRegistry بعمر واضح |

لا تجعل كل شيء global. الحالة العالمية تزيد الترابط وصعوبة التخلص من الموارد.

## Signal

Signal قيمة قابلة للقراءة والتحديث، وتخبر المستهلكين عند تغيرها. استخدمها للحالة الصغيرة التي تحتاج إلى تفاعل.

```ts
const count = state(0)
console.log(count())
count.set((previous) => previous + 1)
```

في بعض أجزاء API قد يكون الاسم `createSignal` أو `state` حسب الحزمة المستعملة؛ اتبع exports في الإصدار المثبت.

## Computed

Computed قيمة مشتقة تُعاد حسابها عند تغير dependencies، مع memoization. لا تجعل Computed يكتب إلى Signal آخر أثناء التقييم؛ فهذا قد ينتج دورة.

```ts
const price = state(100)
const quantity = state(2)
const total = computed(() => price() * quantity())
```

Nexis يكتشف إعادة الدخول في Computed ويعطي تشخيصًا بدل ترك Stack overflow غامضًا. إذا ظهرت رسالة cycle، ابحث عن computed يقرأ نفسه مباشرة أو بصورة غير مباشرة.

### Signal داخل المعالجات الكسولة

عندما يلتقط معالج `onClick$` إشارة أو Store، يضع مترجم production مفتاحًا معتمًا في `data-nx-scope` ويحفظ الحمولة المطلوبة للمتصفح في `nexis-state.js` ليتمكن المتصفح من بنائها عند أول تفاعل. يتطلب ذلك قيمة ابتدائية بشكل JSON حرفي:

```ts
const count = state(0) // ✅ تُسلسل داخل الصفحة
const items = state(load()) // ⚠️ تشخيص unsupported — غير قابلة للتسلسل ساكنًا
```

الالتقاطات غير القابلة للتسلسل تنتج تحذير `unsupported` واضح وقت البناء بدل الفشل الصامت وقت النقر. المعالجات المتعددة التي تلتقط نفس التعليمة تتشارك نفس نسخة Signal الحية في المتصفح عبر scope id.

يقلل أصل state الخارجي metadata الظاهرة في مصدر HTML، لكن محتواه يصل إلى المتصفح ويظل عامًا. تعامل مع ScopeRef باعتباره حدود بيانات عميل، وليس مخزن أسرار. تبقى فحوص تسريب الأسرار وملكية state الخاصة بالطلب مطلوبة.

## Effect

Effect مناسب للآثار الجانبية مثل تحديث عنوان document أو إرسال event محلي. لا تستخدمه بدل Computed لتمثيل قيمة مشتقة.

```ts
effect(() => {
  document.title = `Count: ${count.value}`
})
```

كل Effect يجب أن يُربط بـ root أو owner قابل للتخلص. لا تنشئ Effect على مستوى module إذا كان يعتمد على route أو user.

## Batch

عندما تغير عدة Signals معًا، استخدم batch حتى لا تعيد تشغيل كل Effect بعد كل تحديث.

```ts
batch(() => {
  firstName.set('سارة')
  lastName.set('علي')
})
```

Batch ليس وسيلة لإخفاء تحديثات كثيرة غير ضرورية. استعمله عندما تكون التغييرات جزءًا من transaction واحدة.

## Store

Store يجمع state وselectors وعمليات update في واجهة واحدة. اجعل قيمه serializable إذا كان سيظهر في ScopeRef أو يُستخدم في SSR/Client boundary.

```ts
const cart = createStore({
  items: [],
  total: 0,
})

cart.set((current) => ({
  ...current,
  total: current.total + 20,
}))
console.log(cart.snapshot())
```

تحقق من شكل API الدقيق في حزمة `@mohammedaydan/state`؛ فالـ Store يوفر `scope`, `value`, `snapshot`, `set`, `select`, `subscribe`, و`dispose`.

## Selectors

Selector يجب أن يكون pure قدر الإمكان. لا يغير Store ولا يقرأ الوقت أو random أثناء الحساب، وإلا أصبحت memoization غير مستقرة.

```ts
const itemCount = store.select((value) => value.items.length)
```

عند `dispose` يجب أن يتوقف underlying signal وselector computeds عن استقبال updates أو القراءة، حتى لا تبقى subscriptions معلقة.

## StateRegistry

StateRegistry مفيد عندما تريد تسجيل Stores حسب scope. استخدم IDs مستقرة، وتجنب collision بين routes. عند نهاية route أو session استدعِ disposal المناسب.

## SSR والحالة

لا تستخدم mutable singleton state للخادم إذا كانت البيانات خاصة بالطلب. أنشئ state داخل request أو داخل render owner. مشاركة Signal عالمية بين طلبين قد تسبب تسريب بيانات مستخدم إلى مستخدم آخر.

## Hydrationless state

الـ Signal في Nexis ليس بديلًا عن HTML. إذا كان العنوان أو السعر الأساسي مهمًا، أخرجه في SSR أولًا، ثم استخدم Signal لتحديثه بعد التفاعل.

## قائمة فحص الحالة

- هل يمكن حساب القيمة من Props بدل تخزينها؟
- هل Signal مملوكة لمكون أو route واضح؟
- هل Computed pure ولا يسبب cycle؟
- هل Effect له cleanup؟
- هل Store serializable عند الحاجة؟
- هل `dispose` يُستدعى في route transitions؟
- هل حالة المستخدم معزولة عن الطلبات الأخرى؟
