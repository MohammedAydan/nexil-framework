# 01 — نظرة عامة على Nexis Framework

## ما هو Nexis؟

Nexis Framework هو فريمورك TypeScript لبناء تطبيقات ويب تُخرج HTML من الخادم، وتضيف JavaScript فقط إلى الأجزاء التي تحتاج إلى تفاعل. الفكرة الأساسية هي فصل **إخراج المحتوى** عن **تشغيل السلوك**: الصفحة يمكن أن تكون سريعة وقابلة للفهرسة حتى لو لم يُحمّل أي JavaScript، بينما تُحمّل التفاعلية عند أول استخدام فعلي لها.

هذا النموذج مناسب للمواقع التسويقية، المدونات، لوحات التحكم، المتاجر، صفحات المنتجات، تطبيقات المحتوى، والتطبيقات التي تريد التحكم الدقيق في حجم JavaScript.

## دورة حياة الطلب

عند وصول طلب HTTP، يحدد Router الصفحة المطابقة، ثم يمررها إلى Renderer مع وضع الرندر المطلوب. ينتج Renderer HTML، ويجمع Compiler حدود التفاعل وبيانات `ScopeRef`، ثم يكتب CLI الملفات النهائية. في المتصفح، يعمل Bootstrap صغير لتفويض الأحداث وتحميل chunk المطلوب فقط.

```text
Request
  │
  ▼
Router ──► Route module ──► Renderer ──► HTML + metadata
                                  │
                                  ▼
                           Compiler / Vite plugin
                                  │
                                  ▼
             static files, bootstrap, lazy chunks, assets
                                  │
                                  ▼
Browser event ──► bootstrap ──► lazy chunk ──► handler
```

| الخاصية                 | الفائدة                                                                 |

| SSR وSSG وISR           | اختيار طريقة توليد HTML حسب طبيعة الصفحة                                |
| Resumability            | تحميل سلوك الجزء المتفاعل عند الحاجة بدل إعادة Hydration للتطبيق كاملًا |
| ScopeRef                | نقل مراجع الحالة والأفعال بطريقة موسومة وآمنة                           |
| Typed actions           | معالجة النماذج والطلبات الخادمية مع التحقق من الأصل والتكرار            |
| Router قائم على الملفات | تحويل ملفات `src/routes` إلى مسارات واضحة                               |
| CSS extraction          | إخراج CSS مع تقليل JavaScript في الصفحات الساكنة                        |

## متى تستخدم Nexis؟

استخدمه عندما يكون وقت HTML الأول، الفهرسة، حجم JavaScript، أو التحكم في الخادم مهمًا. وهو خيار قوي عندما توجد صفحات كثيرة ثابتة أو شبه ثابتة، مع عدد محدود من الأجزاء التفاعلية.

قد لا يكون الخيار الأول لتطبيق يعتمد على Canvas كثيف أو لعبة متصفح أو تطبيق داخلي لا يظهر محتوى مفيدًا قبل تشغيل JavaScript. حتى في هذه الحالات يمكن استخدامه، لكن يجب تصميم حدود التفاعل بعناية.

## نموذج التفكير الصحيح

لا تبدأ بسؤال: «كيف أجعل الصفحة كلها Client App؟». ابدأ بسؤالين:

1. ما المحتوى الذي يجب أن يصل كـ HTML؟
2. ما أصغر جزء يحتاج إلى كود متصفح؟

كلما كانت حدود التفاعل أصغر، استفدت أكثر من Nexis. المكون الساكن يجب أن يبقى JSX/HTML فقط، أما الزر أو البحث أو النموذج فيجب أن يملك Handler مستقلًا.

## ما الذي لا يفعله Nexis تلقائيًا؟

لا يحول أي Closure عشوائي إلى بيانات قابلة للنقل، ولا يخمّن كل حالة في التطبيق، ولا يوفر قاعدة بيانات أو نظام تسجيل دخول مدمجًا، ولا يجعل التخزين process-local مناسبًا تلقائيًا للتشغيل متعدد النسخ. هذه مسؤوليات يجب تصميمها على مستوى التطبيق أو البنية التحتية.

## الخلاصة

Nexis ليس مجرد SSR تقليدي، وليس SPA تقليديًا. هو نموذج **HTML أولًا + تفاعلية انتقائية + حالة موسومة + ميزانيات قابلة للقياس**. نجاح المشروع يعتمد على اختيار حدود واضحة بين الصفحة الساكنة والسلوك المتفاعل.
