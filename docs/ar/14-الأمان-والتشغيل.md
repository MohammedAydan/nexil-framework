# 14 — الأمان والتشغيل

## نموذج التهديد

اعتبر كل input من المتصفح غير موثوق، بما في ذلك pathname وquery وheaders وcookies وmultipart files وredirect targets. اعتبر أيضًا أن أي client bundle مكشوف للمستخدم، لذلك لا تضع فيه سرًا أو authorization decision.

## طبقات الحماية

| الطبقة     | الحماية                                    |
| ---------- | ------------------------------------------ |
| Renderer   | Escape للنصوص والخصائص                     |
| SEO        | التحقق من URL وJSON-LD escaping            |
| Router     | رفض traversal ومطابقة آمنة                 |
| Server     | method allowlist وbody limit وcache policy |
| Actions    | Origin وvalidation وIdempotency            |
| Deployment | TLS وproxy sanitation وrate limits         |
| Operations | logs آمنة وalerts وrollback                |

## XSS

لا تدخل HTML من المستخدم مباشرة. استخدم text nodes أو sanitizer موثوقًا ومحددًا. JSON-LD يجب أن يهرب `<` و`>` و`&` حتى لا يكسر script context.

## SSRF

إذا كان الخادم يجلب URL قدمه المستخدم، طبّق allowlist للـ protocol والhost، امنع private IP ranges، ضع timeout وحجمًا أقصى، ولا تتبع redirects إلى نطاقات غير مسموحة.

## Actions وCSRF

Origin check مهم لكنه ليس authorization. بعد التحقق من الأصل، افحص جلسة المستخدم وصلاحياته وملكية المورد. استخدم CSRF token أو SameSite cookies حسب threat model، خصوصًا للعمليات الحساسة.

## Proxy headers

لا تثق في `x-forwarded-proto` أو `x-forwarded-host` إلا إذا كان proxy موثوقًا يزيل قيم العميل ويكتب قيمه. الإعداد `NEXIS_TRUST_PROXY=1` opt-in، وليس حلًا عامًا لأي استضافة.

## Cookies

الإعدادات الموصى بها للجلسات:

```text
HttpOnly; Secure; SameSite=Lax
```

اختر `SameSite=Strict` إن كان مناسبًا، وحدد `Path` و`Max-Age`. لا تخزن secrets في localStorage.

## Headers

استخدم `createSecurityHeaders` أو إعدادًا مكافئًا لإضافة Content-Type وCSP وReferrer-Policy وX-Content-Type-Options حسب التطبيق. لا تضف CSP عشوائيًا يكسر assets؛ ابدأ بسياسة report-only ثم شددها.

## Secrets

- لا تضع `.env` في Git.
- لا تمرر `process.env.SECRET` إلى JSX.
- لا تطبع request headers أو tokens في logs.
- استخدم secret manager في الإنتاج.
- نفّذ rotation وخطة إبطال.

## Rate limits وbody limits

ضع limit للنماذج والـ telemetry، وrate limit حسب IP/session/user، مع حماية من burst. body limit في Node layer ليس بديلًا عن CDN/WAF limit.

## Idempotency والتوزيع

التخزين process-local مناسب للاختبار أو نسخة واحدة فقط. في multi-instance، استخدم storage مركزيًا durable مع TTL، وحماية من memory growth، وآلية atomic claim للمفتاح.

## Telemetry والخصوصية

Web Vitals قد تكون بيانات مرتبطة بسلوك المستخدم. اجمع الحد الأدنى، لا تسجل URLs حساسة أو query سرية، طبّق consent عند الحاجة، وحدد retention وaccess policy. receiver المحلي لا يعني أن governance اكتملت.

## Dependency security

شغّل `pnpm audit --audit-level=high`، راجع lockfile، وثبت الإصدارات. افحص الحزم الجديدة، خاصة أدوات build التي قد تنفذ code في بيئة CI.

## Incident readiness

يجب أن تملك:

- logs منظمة بلا أسرار.
- correlation/request ID.
- health endpoint.
- metrics للـ 4xx/5xx والـ latency.
- rollback إلى build سابق.
- backup للإعدادات وبيانات Actions.
- runbook للحوادث.

## قائمة فحص قبل الإنتاج

- هل كل Action تتحقق من auth وinput وOrigin؟
- هل proxy headers موثوقة فعلًا؟
- هل private HTML ممنوع من shared cache؟
- هل paths تمنع traversal؟
- هل الصور الخارجية allowlisted؟
- هل CSP والcookies مراجعان؟
- هل telemetry يحترم الخصوصية؟
- هل idempotency durable إذا كانت العملية مهمة؟
