# 08 — Actions والنماذج والطلبات الخادمية

## ما هي Action؟

Action هي وظيفة خادمية تُنفذ عبر endpoint مخصص. تستخدمها لمعالجة نموذج، إنشاء سجل، إرسال رسالة، أو تنفيذ عملية تتطلب صلاحيات الخادم. لا ترسل جسم الوظيفة أو أسرارها إلى العميل؛ العميل يحمل مرجعًا وبيانات الطلب فقط.

## النموذج الصحيح

ابدأ بنموذج HTML يعمل بدون JavaScript:

```tsx
<form action="/__nexil/actions/contact/submit" method="post">
  <label for="email">البريد</label>
  <input id="email" name="email" type="email" required />
  <button type="submit">إرسال</button>
</form>
```

للمسار المعتاد استخدم `Form` و`SubmitButton`. يحافظان على الإرسال الأصلي ويضيفان metadata لتشغيل `nexil-forms.js`. استخدم `onSubmit$` عندما تحتاج إلى عرض نتيجة مخصص، مع إبقاء `action` و`method` الحقيقيين كخطة احتياطية.

```tsx
import { Form, SubmitButton } from '@nexil/core'
import { action } from '@nexil/actions'

const contactAction = action({
  endpoint: '/__nexil/actions/contact/submit',
  validate: (input) => input,
  handle: async (_context, input) => saveContact(input),
})

export function ContactForm({ csrfToken }: { readonly csrfToken: string }) {
  return (
    <Form action={contactAction} csrfToken={csrfToken}>
      <input name="email" type="email" required />
      <SubmitButton loadingText="Sending…">Send</SubmitButton>
    </Form>
  )
}
```

يقوم runtime بالحفاظ على الحقول المتكررة، وإرسال `Idempotency-Key` و`X-CSRF-Token` الاختياري، وتعطيل الزر مؤقتًا، وإطلاق أحداث النجاح والفشل.

## مراحل Action transport

ينفذ transport الخطوات التالية بالترتيب:

1. يتحقق من HTTP method.
2. يحدد Content-Type ويحلل JSON أو URL-encoded أو multipart.
3. يطبق حد حجم الطلب.
4. يتحقق من Origin وسياسة الموقع.
5. يتحقق من schema والبيانات.
6. يطبق `Idempotency-Key` ويرفض التكرار داخل فترة الاحتفاظ.
7. يتحقق من `X-CSRF-Token` عند تفعيل حماية CSRF.
8. ينفذ handler الخادمي.
9. يعيد envelope typed:

```ts
{ ok: true, data: result }
{ ok: false, errors: ['Invalid email'] }
```

## التحقق

لا تعتمد على validation في المتصفح وحده. تحقق في الخادم من النوع والطول والقيم المسموح بها. افصل validation عن authorization؛ صحة البيانات لا تعني أن المستخدم يملك صلاحية العملية.

```ts
const input = parseContactInput(await request.formData())
if (!input.email.includes('@')) {
  return { ok: false, errors: [{ field: 'email', message: 'البريد غير صالح' }] }
}
```

## Origin وCSRF

الـ server يتحقق من Origin حتى لا يقبل POST من موقع آخر. لا تضع `NEXIL_TRUST_PROXY=1` إلا خلف Proxy موثوق ينظف `x-forwarded-proto` و`x-forwarded-host`. إذا كانت هذه headers قابلة للتزوير، قد يصبح فحص الأصل غير موثوق.

حدد Origins المسموحة صراحة في الإنتاج، ولا تجعل `*` سياسة عامة لنماذج تغير بيانات.

## Idempotency

إذا كان الطلب قد يُعاد بسبب retry أو ضعف الشبكة، أرسل `Idempotency-Key`. المفتاح يمنع تنفيذ العملية مرتين داخل فترة صلاحية التخزين.

المخزن الافتراضي process-local. لذلك لا يكفي في multi-instance deployment. استخدم adapter durable مثل Redis أو قاعدة بيانات، مع TTL وحد أقصى للحجم، إذا كانت العملية مالية أو غير قابلة للتكرار.

## Cookies وAuthorization

لا تضع authorization داخل hidden input. استخدم جلسة خادمية أو cookie آمنة. راجع `HttpOnly` و`Secure` و`SameSite` ومدة الانتهاء. لا تسجل tokens أو جسم الطلب كاملًا في logs.

## Receiver Telemetry

الـ production server يدعم receiver اختياريًا على `POST /__nexil/telemetry`. يقبل envelope object صالحًا ويعيد `202`، ويرفض body غير صالح بـ `400`. هذا receiver نقطة بداية محلية، وليس نظام ingestion كاملًا.

## أخطاء شائعة

| الخطأ                                   | الحل                                                     |
| --------------------------------------- | -------------------------------------------------------- |
| تنفيذ mutation من GET                   | استخدم POST أو method مناسب                              |
| validation في العميل فقط                | أعد التحقق في الخادم                                     |
| قبول Origin عشوائي                      | allowlist صريح                                           |
| Idempotency process-local مع نسخ متعددة | storage مركزي durable                                    |
| إعادة رسالة خطأ داخلية للمستخدم         | رسالة عامة وتسجيل داخلي آمن                              |
| تشغيل action داخل client bundle         | ضع التنفيذ في server module                              |
| نسيان حالة التحميل                      | استخدم `SubmitButton loadingText` و`aria-live`           |
| اعتبار client enhancement حماية أمنية   | أعد التحقق والتفويض وOrigin وCSRF وidempotency في الخادم |

## اختبار Action

اختبر النجاح، الإدخال الخاطئ، Origin المرفوض، method الخاطئ، duplicate idempotency key، body كبير، وانقطاع الاتصال. اختبر كذلك أن النموذج يعمل native عندما لا يحمل JavaScript.
